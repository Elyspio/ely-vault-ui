# Security model

[← Documentation](../README.md)

- **The renderer never receives secrets in bulk**: the items are stripped by the main process (`vault.mapper.ts`). Each secret is requested on demand (show, copy, type), by id.
- **Copy by the main process**: the clipboard is cleared after the configured delay if it still holds the value. On Windows, copied values are excluded from the clipboard history and the cloud clipboard.
- **Master password re-entry** for "reprompt" items, checked offline (scrypt hash in memory), valid for 5 minutes.
- **Locking**: manual (`Ctrl L`), after inactivity, when the session locks, when the computer sleeps and on quit (`bw serve` is stopped).
- **Offline access expires after 24 hours**: only a successful authenticated, forced vault sync renews access to the entire cached vault. The main process locks open sessions at expiry, clears held secrets and owned clipboard content, and blocks reveal, copy, auto-type and writes. It syncs on unlock and resume, and every 15 minutes while unlocked. Network failures permit only the remaining offline window (the CLI runs with `--unhandled-rejections=warn`, so a failed token refresh does not stop `bw serve` and lock the vault); explicit authentication rejection requires online sign-in again. Missing, corrupt, future or rolled-back time evidence requires a successful online sync, including the first unlock after upgrading. Verification evidence is scoped to the account and server in `offline-access.json`. The window can only be shortened, with the *Offline access* setting (`security.offlineAccessMinutes` in `config.json`, 1 to 1440 minutes; larger values are lowered to 24 hours) applied at once to the open session; no setting disables the limit or extends it beyond 24 hours. The encrypted CLI cache is retained on expiry.
- **Electron hardening**: `sandbox`, `contextIsolation`, no `nodeIntegration`, strict CSP, blocked navigation and new windows, web permissions denied, IPC only accepted from the application page, only `http(s)` links opened, restricted Electron fuses.
- **Certificates**: no "ignore TLS errors" option. When the system refuses the server certificate, the application completes the chain through the AIA URLs (each downloaded certificate must have signed the previous one), shows the root authority and its SHA-256 fingerprint, and only approves it after confirmation. An authority certificate can also be imported (`.crt`, `.cer`, `.pem`). The approved authorities are passed to the CLI (`NODE_EXTRA_CA_CERTS`) and to Chromium, and are removed in **Settings → Certificates**.
- **Write-only secrets**: in an edit, a secret is sent by the renderer only when the user typed or cleared it. Otherwise the main process keeps the stored value from the raw item. Secrets never enter the Redux store.
- **Full raw item on every edit**: the CLI replaces nested objects (login, card, fields) with what it receives, so the main process always starts from `GET /object/item/:id` and applies the changes on top. Passkeys, password history and other unknown properties are not lost.
- **Settings while locked or logged out**: only the display and update sections are shown, and the main process ignores changes to the other settings until the vault is unlocked.
- **Windows Hello unlock** (opt-in, Windows): the master password is encrypted with the Windows user's key (DPAPI through Electron `safeStorage`) in `hello-unlock.json`, for one account, and only decrypted in the main process after a Windows Hello verification (`UserConsentVerifier` through WinRT, koffi). It is offered right after a master password unlock: the main process keeps that password encrypted in memory for 5 minutes (vault unlocked only), so accepting does not send it again from the renderer. The stored password is deleted on logout and when it no longer unlocks the vault. Its dialog opens by itself only on the first unlock screen after startup; after a lock, the user starts it. Once offline access expired, the main process first checks that the vault server answers (`/alive`, 5 seconds): when it does not, no Windows Hello dialog opens and the unlock screen tells that the server is unreachable (same check before a master password unlock).
- **Private SSH keys never reach the renderer**: generated or imported keys stay in the main process behind a random one-time token, expiring after 10 minutes, cleared on lock and logout. Only the public key and the fingerprint are shown. Passphrases and key material are never logged.
- **Reprompt enforced in the main process** for editing, moving to the trash, permanent deletion, and revealing, copying or auto-typing a secret of protected items.
- **Clipboard QR codes**: the screenshot is decoded in the main process; only a valid TOTP value goes back, and other QR codes are refused without echoing their content.
- **No secret in the logs**: the log decorator records neither parameters nor return values.

> **Known limitation**: `bw serve` has no authentication. While the vault is unlocked, a local process that finds the port can read it (browser requests are refused by the CLI through its `Origin` header check). This is the same model as `bw serve` used on its own.

> **Known limitation**: the offline deadline is an ElyVault safeguard, with best-effort clock rollback detection. Someone controlling their computer can bypass it with modified clients, copied CLI caches or exported secrets. Rotate shared credentials when offboarding collaborators; the app cannot revoke secrets already obtained.

> **Known limitation**: Windows Hello unlock is a user consent check, not a key derived from Windows Hello. Malware running as the same Windows user can decrypt the stored master password through DPAPI without the Windows Hello dialog. Leave it off when this matters.
